# Individual Reflection – Axel Bauer (Axel), Developer

My technical contribution was Part E, restricting the demonstration database reset operation to authorized staff members (Jira story CF-17, bug CF-22), as well as verifying staff status transitions and mandatory resolution notes (Jira stories CF-13 and CF-14, test case TC-09). In the initial version, `/api/reset-demo` had no role check, allowing any student session to wipe submitted reports and re-seed the database. I fixed this in branch `E-reset-guard` and pull request #4. In `app.py`, `reset_demo()` now verifies `session.get('role', 'student') == 'staff'` and rejects non-staff requests with HTTP 403 Forbidden. In `static/js/app.js`, `updateUserRoleUI()` visually disables the `#card-nav-reset` card for students, and `resetDemoData()` displays the server error alert when a 403 response is returned. I added `tests/test_E_reset_guard.py` with six unit tests covering staff reset success, default seed restoration, custom report purge, idempotency across repeated calls, HTTP 405 on GET requests, and student 403 rejection while asserting that existing reports remain untouched in SQLite. I also reviewed pull requests #5, #7, and #8 for Part D.

One difficulty I encountered was test configuration and review feedback. Initially, my test file was placed in a nested `tests/tests/` directory where `unittest discover` did not execute it, and the test client ran under the default student session instead of configuring the `staff` role in `setUp()`. After fixing the backend guard and test location, a teammate's review on PR #4 also highlighted that clicking the reset card as a student showed no error toast in the UI and that the 403 test should explicitly verify data preservation.

One improvement for next time is to check every acceptance criterion end-to-end—covering backend validation, frontend user feedback, and database state assertions—before opening a pull request.
